# Decisions (lightweight ADRs)

## ADR-1: Express 5 over Fastify and NestJS
- **Context:** The app is a JSON API with one resource and a few aggregate endpoints. The UI is a separate React SPA. The role is Node.js, so the framework should be one reviewers know well.
- **Decision:** Express 5 with zod for validation, structured as routers → services → repositories by hand.
- **Trade-off:** Express is the most familiar choice, and version 5 forwards rejected async handlers to the error middleware, removing the old `try/catch` boilerplate. We give up Fastify's built-in schema validation and speed, and NestJS's enforced module structure and DI. At 10,000 rows Express overhead is a fraction of a millisecond, and a `createApp(deps)` factory gives the dependency injection tests need without a framework.

## ADR-2: One shared zod package for the API contract
- **Context:** TypeScript on both sides means the request shape, the validation rules and the response types can be written once instead of mirrored by hand.
- **Decision:** An npm workspace package, `@acme/shared`, holds the country↔currency map, the zod input/query schemas, the business-rule check and the response types. The backend validates with it; the frontend form runs the same rules and imports the same types.
- **Trade-off:** Client and server can't drift, and a contract change fails type-checking on both sides. The cost is workspace setup and one more package. The package ships TypeScript source (no build step): Vite compiles it for the browser and `tsx` runs it on the server (ADR-9).

## ADR-3: SQLite via Drizzle ORM, kept swappable
- **Context:** 10,000 rows, one HR user at a time, and an app that should be easy to run and deploy.
- **Decision:** SQLite through `better-sqlite3` and Drizzle ORM. The table is defined in TypeScript, migrations are generated by `drizzle-kit` and committed, and only repositories write queries.
- **Trade-off:** Drizzle is a thin, typed SQL builder: `GROUP BY` aggregations read like the SQL they produce, and result types are inferred. There's no server to run and tests use fast in-memory databases. `better-sqlite3` is synchronous, which is simpler and faster for SQLite, but would be swapped for an async driver with Postgres. Only one process can write at a time, and durable data needs a persistent disk (ADR-10).

## ADR-4: Salary as integer minor units, not float
- **Context:** Floats can't represent most decimal amounts exactly (`0.1 + 0.2 ≠ 0.3`), so sums and averages pick up rounding errors. JavaScript has only one number type.
- **Decision:** Store `salary` as an integer in minor units (cents, paise), with a per-currency count of minor-unit digits (JPY = 0). zod rejects non-integers. The form converts typed text to minor units with string manipulation, not float maths. Format only in the UI.
- **Trade-off:** Storage and arithmetic are exact, and the cap of 10^12 keeps every value far inside `Number.MAX_SAFE_INTEGER`. The cost is conversion at the edges and remembering that `AVG` returns a fraction, which is rounded once in the service.

## ADR-5: Per-country insights, no FX conversion
- **Context:** Salaries are in local currencies. Org-wide salary figures would need FX rates and a date for those rates.
- **Decision:** Salary statistics are only computed within a country, in its currency. The org summary shows only counts (headcount, countries, departments).
- **Trade-off:** Every number shown is correct. HR can't compare pay across countries in one figure, which is the most likely future request. Adding it would mean an FX table with dated rates.

## ADR-6: Aggregations in SQL
- **Context:** Insights need min, max, average and count per group across 10,000 rows.
- **Decision:** Use `GROUP BY` queries in the repository and return only the aggregated rows.
- **Trade-off:** This is fast and memory-light, and it keeps working as data grows. Repository logic is SQL, so tests use a real (in-memory) SQLite rather than mocks. Medians and percentiles would need window functions or JavaScript, and they're out of scope.

## ADR-7: Server-side pagination, filtering and sorting
- **Context:** Sending 10,000 rows to the browser is slow and wastes memory. The success criterion is under 300 ms for the list.
- **Decision:** The API takes `page`, `page_size` (max 100), search, filter and sort parameters, and returns `{ items, total }`. It uses offset pagination, and sorting only on allowed columns (mapped to Drizzle columns, never interpolated).
- **Trade-off:** Each response is small and quick. Every filter change costs a round trip; a short delay on search typing keeps the number of calls down. Offset paging slows down for pages far into the result, which isn't a problem at 10,000 rows (keyset paging would fix it later).

## ADR-8: No authentication
- **Context:** There is one persona and the data is seeded and fake. This is a time-boxed assessment.
- **Decision:** No login and no roles.
- **Trade-off:** We save significant time and keep the app simple. The deployed app is publicly editable, which is acceptable for fake data only and is documented clearly. A real rollout would start with SSO and an HR role before anything else.

## ADR-9: Run TypeScript with `tsx`, no backend build step
- **Context:** The backend imports `@acme/shared` as TypeScript source. Compiling with `tsc` would need the shared package built first and import paths rewritten for Node ESM.
- **Decision:** Run the server, seed and benchmark with `tsx` in development and production. `tsc --noEmit` type-checks everything in CI.
- **Trade-off:** One runtime path everywhere and no build artefacts to keep in sync. The cost is `tsx` as a runtime dependency and a few hundred milliseconds of extra startup for on-the-fly transpilation, irrelevant for a long-running server. If startup time mattered, an `esbuild` bundle would replace it.

## ADR-10: Demo hosting with Render free + ephemeral SQLite, Vercel for the SPA
- **Context:** The brief asks for deployed software, and the stack is SQLite. Render's free web service has an ephemeral filesystem and spins down after 15 minutes idle. Its free Postgres expires after 30 days.
- **Decision:** The API runs on Render free with SQLite on the instance disk and seeds 10,000 employees on startup only when the DB is empty. The SPA is a static Vite build on Vercel, pointed at the API with `VITE_API_BASE_URL`, with CORS allowing only the configured origins.
- **Trade-off:** It's free and needs no code changes. Every redeploy, restart or spin-down resets the data to the seed, and the first request after idling is slow. That's acceptable for a demo with fake data and is documented in [deployment.md](deployment.md). For durable data, switch the driver to Postgres (e.g. Neon free): Drizzle's `pg-core` table, an async driver, and a Postgres CI job.
